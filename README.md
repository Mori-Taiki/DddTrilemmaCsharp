# DDDトリレンマをC#の型で扱う

ストーリーの閲覧判定と公開範囲変更を題材に、判断を純粋なドメインに集め、I/Oを外側で実行するサンプルです。C# 15 / .NET 11、ASP.NET Core Minimal API、EF Core、SQLiteで動きます。

## DDDトリレンマ

ドメインモデルには、次の3つを両立したいという要求があります。

- **完全性**：業務上の判断がドメインに集まっている。
- **純粋性**：外部状態やI/Oに依存せず、入力した値から結果が決まる。
- **性能**：判断に必要なデータだけを取得する。

例えば「フォロワー限定の作品を読めるか」はDBのフォロー情報が必要です。ドメインがDBを呼べば純粋性を失い、先に全情報を取得すれば不要なクエリが増え、取得の要否をアプリケーションで判断すれば業務ルールが外へ漏れます。これが[DDDトリレンマ](https://enterprisecraftsmanship.com/posts/domain-model-purity-completeness/)の問題です。

## コンセプト：必要な事実を型で返す

着想は、Goの実装記事[「ドメインモデル貧血症はなぜ生まれるのか — Decision パターンで DDD トリレンマを解く」](https://zenn.dev/tellernovel_inc/articles/0193eb68cabb6e)です。記事の「判断するために何が要るか」を型で返す、という考え方をC#で実装しています。

ドメインは、答えが出れば許可・拒否を返し、事実が足りなければフォロー・会員・購入の確認要求を返します。アプリケーションは要求された事実だけを取得し、その値で判定を再開します。取得の実行は外側、何を必要とするかの判断はドメインに残ります。

本実装では、`閲覧判定` を `判定完了(閲覧結果)` と `事実取得待ち(事実要求)` に分けています。作者本人や無料公開なら追加取得なし、非フォロワーなら会員・購入の確認前に打ち切ります。ここでの性能は**単件判定の不要な取得を避けること**であり、一覧のN+1や複数クエリ間の一貫性は別途設計が必要です。

## Discriminated unionと網羅性

Discriminated union（判別共用体）は、有限のケースと、それぞれに必要なデータをひとつの型で表します。「終了したか」というフラグと任意のデータを組み合わせる代わりに、状態ごとに持てる情報を決めます。

```csharp
public closed record 閲覧判定;
public sealed record 判定完了(閲覧結果 結果) : 閲覧判定;
public sealed record 事実取得待ち(事実要求 要求) : 閲覧判定;
```

全ケースを列挙したswitch式では、ケース追加時の処理漏れをコンパイラが検出できます。本実装は `CS8509` をエラー化し、ドメインのケース分岐に `_` を置きません。公開範囲・料金区分・判定・事実要求・終端結果の追加漏れを、ビルド失敗として検証しています。これは分岐の網羅性の保証であり、業務ルールの正しさや処理の終了性まで保証するものではありません。

## 関数型ドメインモデリング

ドメインは不変な値を受け取り、結果を値で返します。`ストーリー` はgetのみのプロパティを持ち、`公開範囲を変える` は自身を書き換えず、`変更できた(変更後)` または `変更拒否(理由)` を返します。中間の事実要求も、不変なストーリーを保持します。

作品には `ストーリーID`、作者・閲覧者・実行者には共通の `利用者ID` を使います。空のIDや未知の公開範囲は境界で拒否し、内部では検証済みの型を扱います。業務上の拒否は結果の型に含め、DB障害・タイムアウトは技術的な例外として外側へ伝えます。

型・メソッド・プロパティは日本語の業務語彙、変数・通常の仮引数は英語のcamelCaseです。実装は [Domain](Domain)、仕様を表す日本語のテストは [Tests](Tests) にあります。

## C# 15：union宣言とclosed階層の違い

参考：[「C# 15のclosed recordとJSONについての検証記事」](https://zenn.dev/jtechjapan_pub/articles/csharp15-closed-record-json)。この実装の「closed union」は、`closed record` と `sealed record` で構成する閉じた継承階層を指します。

| | `union` 宣言 | `closed record` |
|---|---|---|
| 表現 | 共通基底型のない型も束ねる値型 | 共通基底型を持つ参照型の階層 |
| ケース集合 | union宣言に列挙する | 直接の派生を同じアセンブリに制限し、コンパイラが把握する |
| 初期値 | `default` で内部値がnullの空状態が生じる | 基底は暗黙にabstract。ケースのインスタンスを生成する |
| 注意点 | 宣言したケースに加え、空状態も扱う必要がある | 参照のnullは残るため、nullable解析と境界での検証が必要 |

どちらも網羅性検査の対象ですが、本モデルでは**業務ケース以外の空状態を増やさないclosed階層の方が、網羅性を保ちやすい**と考えて採用しています。`closed` だけで実行時のnullを禁止できる、という意味ではありません。末端を `sealed` にし、ケースを追加したら利用側も再コンパイルして検出します。

## EF CoreとCommand / Query

EF Coreは、POCOにFluent APIで永続化を後付けでき、DbContextが変更追跡とUnit of Workを担います。DDDを実践するために、DbSetの操作をそのまま包む汎用Repositoryを重ねる必要はありません。可変なドメインエンティティを直接追跡させる方法も自然です。

本実装は不変性を優先し、ドメインの `ストーリー` とEFが追跡する `ストーリー行` を分けています。変換コードを持つ代わりに、ドメインへsetterやEF用コンストラクタを持ち込みません。

| | Query：閲覧判定 | Command：公開範囲変更 |
|---|---|---|
| ドメインの役割 | 必要な事実と最終結果を返す | 変更後の状態または拒否を返す |
| EF Coreの役割 | 事実取得ポートの内側で `AnyAsync` を実行 | 追跡中の行へ変更を適用し `SaveChangesAsync` |
| 境界の意味 | テーブル構造を業務上の質問へ変換する | 保存・トランザクションをアプリケーションで管理する |

```csharp
var result = row.ドメインに戻す().公開範囲を変える(newVisibility, actor);
if (result is 変更できた changed)
{
    row.適用する(changed.変更後);
    await db.SaveChangesAsync(ct);
}
```

Queryは事実を読む処理、Commandは状態を保存する処理なので、DbContextとの境界も異なります。読み書きは同じSQLiteを使い、別DBやイベントソーシングは導入していません。

## 動かし方

[GitHub Codespacesで開く](https://codespaces.new/Mori-Taiki/DddTrilemmaCsharp)と、SDKの準備・依存関係の復元・ビルドが自動で行われます。ローカルでは.NET SDK **11.0.100**を導入して、このリポジトリをcloneしてください。以下はリポジトリ直下で実行します。

```bash
dotnet run --project Api -- --urls http://0.0.0.0:5080
```

Codespacesでは **Ports → 5080**、ローカルでは `http://localhost:5080` を開きます。`Api/app.db` は初回起動時にサンプルデータとともに作成されます。DBサーバーの準備は不要です。

```bash
curl 'http://localhost:5080/stories/followers-paid/view?viewer=vip'
curl -X PUT http://localhost:5080/stories/public-free/visibility \
  -H 'Content-Type: application/json' \
  -d '{"actor":"author","visibility":"フォロワー限定"}'
dotnet test Tests/Tests.csproj
```

`viewer` を `guest`・`follower`・`vip`・`buyer`・`author` に変えると、結果・判定経路・追加クエリ数を比較できます。利用者指定はデモ用で、認証ではありません。型の網羅性は `python3 scripts/check_exhaustiveness.py` で検証できます。

## 更なる可能性

[SoutherによるDDDトリレンマへのアプローチ](https://zenn.dev/kawasima/articles/souther-ddd-trilemma)は、途中状態を手で型にする負担から一歩進み、振る舞いの契約と合成可能性に注目しています。モデル内の判断と外部I/Oを区別し、業務結果と技術的失敗を別経路で扱う点は本実装とも共通します。

次の方向として、入出力の関係を事後条件で表すこと、仕様例の不足を機械的に検出すること、同じ仕様例を外部実装の契約テストにも使うことが考えられます。C#の網羅性検査は「ケースを書き忘れていない」を支えますが、**何が正しい業務結果なのかを仕様として表し、実装と照合すること**は、その先にある課題です。
